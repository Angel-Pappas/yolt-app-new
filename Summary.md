# Summary

This file exists so a fresh session can get up to speed on this app quickly. Keep it current: update the relevant section whenever a major feature is added, removed, or changed.

## General description

Yolt-App is an all-encompassing company app, **multi-user since 2026-08**, split into two **areas**: **Finance** (the original financial transactions tracker) and **Business** (a basic CRM — leads). A **super admin** invites users by email and grants each one Finance and/or Business access; financial and CRM data are **shared company data**, gated by permission (not per-user ownership). See the dedicated **"Multi-user, areas & access control"** section below for the whole model — that section supersedes older per-page framing in this file (the Options/Account/Lists pages have since merged into a unified Settings area).

The **Finance** area supports logging typed transactions (Income, Expense, or Transfer between wallets — date, invoice date, entity, category, wallet(s), description, net amount, VAT) behind email/password authentication, plus supporting lists of Entities, Wallets, reference/lookup lists (VAT rates, Withheld tax rates, Categories — now under Settings), and a Taxes section with auto-computed monthly VAT and withholding-tax breakdowns. Transactions also carry optional **withholding tax** (2026-08 — kept back from a contractor's fee and remitted to the state, so Total = net + VAT − withheld). The **Business** area is the CRM (Leads with an activity log, plus **Projects** — a lead that's been won graduates into a tracked project; 2026-08). Planned future features include financial projections, automatic generation of recurring transactions, more tax types beyond VAT and withholding, a real notifications system (currently a placeholder — the bell in the top bar), business-area growth (projects, project states), plus whatever else comes up as the app grows.

## Multi-user, areas & access control (2026-08)

The single biggest change since the app's single-user origins. Built in phases; the full plan lives in `Plan-Multi-User-and-CRM.md`.

- **Permissions live on a `profiles` table** (one row per auth user): `is_admin`, `can_access_finance`, `can_access_crm`, `is_active`, plus `email`/`full_name` (denormalized). Chosen over JWT-baked custom claims **deliberately** — a profile read fresh each request means an admin's access change applies *immediately* (no token-refresh lag), and three booleans don't warrant a roles/permissions matrix. If fine-grained permissions are ever needed, grow the helpers, not the call sites.
  - **Permission helpers live in a `private` schema** (not `public`), so they're not exposed as PostgREST RPCs: `private.is_admin()`, `private.has_finance_access()`, `private.has_crm_access()`, `private.is_active_user()` — all `SECURITY DEFINER STABLE`, so reading `profiles` inside them doesn't re-trigger `profiles`' own RLS (no recursion), and wrapped in `(select …)` at RLS call sites for the InitPlan perf pattern. `authenticated` has USAGE on `private` + EXECUTE on these; `anon`/`public` do not. Write new internal helpers here, not `public`.
  - **`private.handle_new_user()`** (trigger on `auth.users` insert) auto-creates a bare profile (all access false, active true) for every new user; the invite flow then sets the chosen flags.
  - `profiles` RLS: SELECT self-or-admin; a self-update policy + a column-level `GRANT UPDATE (full_name)` lets a user edit only their own display name (never their flags); admin flag writes go through the **service-role** admin client, which bypasses RLS entirely.
- **Shared company data**: every finance table's RLS was converted from `(select auth.uid()) = user_id` to `(select private.has_finance_access())` (SELECT/INSERT/UPDATE; INSERT also pins `user_id = auth.uid()` so authorship can't be forged). `user_id` stays as a created-by audit field, no longer the access gate. The CRM tables use the equivalent `has_crm_access()` gate. The `security_invoker` views (`transactions_expanded`, `wallet_balances`) inherit these automatically. Verified: a finance user sees all rows, a no-access user sees zero.

(Confirmed empirically: following a spent invite link landed on `/auth/auth-code-error#error=access_denied&error_code=otp_expired`, error in the fragment, query string empty → implicit flow.) This is what makes the **default** Supabase email work with no SMTP and no template edit. `/set-password` is deliberately **not** in the proxy allow-list — it needs a live session for `updateUser`; the fix delivers that session (via the cookies `setSession` writes) rather than exposing the page without one. ## Main sections of the app

- **Authentication** — Signup, login, and logout. Email/password via Supabase Auth, including the email-confirmation flow. Pages: `/login`, `/signup`, `/auth/confirm` (confirmation link handler), `/auth/auth-code-error` (expired/invalid link fallback).
- **Home** (`/`) — Minimal landing page after login. Placeholder content for now.
- **Transactions** (`/transactions`) — Full CRUD on transactions (date, type, entity, category, wallet(s), description, net, VAT rate), all backed by RLS-scoped Server Actions (`actions.ts`: `addTransaction`, `updateTransaction`, `deleteTransaction`).
  - **Add**: a text "Add" button opens a modal (`transaction-modal.tsx`).
  - **Edit**: no button — clicking anywhere on a transaction's row (`transaction-row.tsx`, a client component) opens the same edit modal, pre-filled.
  - **Delete**: a trash-icon button per row (`delete-transaction-button.tsx`, `src/components/icons.tsx` for the icon — inline SVG, no icon library dependency); its click handler (and the dialog's) calls `stopPropagation()` so it doesn't also trigger the row's edit-open behavior. Delete is a **soft delete** — see the Database section below. Nothing is ever hard-deleted through the app.
  - **Reconcile** (2026-07, `reconcile-button.tsx`/`reconcile-modal.tsx`, `is_reconciled` column) — a check-circle button that opens a **reduced** edit modal: only Date, Amount, and Wallet(s) are editable (no description/entity/VAT rate). This is why `getActiveTransactions`/`getWalletTransactionsWithBalance` take **`offset`/`limit` rather than `page`/`pageSize`** — re-fetching an arbitrary already-loaded span isn't expressible as a page number. That `loadMore` reads the stale length and fetches the span the re-sync is simultaneously putting back (the new row sits at the bottom under the default `date asc` sort, i.e. exactly that offset), and the in-flight append lands *after* the synchronous re-sync `setRows`, doubling the new row. `loadMore` assuming the loaded rows are a contiguous prefix of the server list is what breaks when a mutation grows the list mid-fetch; keying the append makes an overlapping fetch a harmless no-op.     - **Every column has a working header filter now** (2026-07, explicit user direction — "the filter button should be visible and working for all columns regardless of their content," everywhere in the app, not just Transactions): Type/Wallet/Category/Entity use the existing categorical `HeaderFilterPopover` (an options list); Date uses the new `HeaderDateRangeFilterPopover`, deliberately bound to the *same* `from`/`to` params as the toolbar's `DateRangeFilter` rather than a second, disagreeing filter; Description uses the new `HeaderTextFilterPopover`, likewise bound to the same `q` param the toolbar `SearchBox` already uses; Net/VAT/Total use the new `HeaderNumberRangeFilterPopover` (min/max).     - **Sorting is tri-state** (2026-07, explicit user direction, replacing a plain asc/desc toggle): unsorted → descending → ascending → unsorted, cycling on repeated clicks of the same header; unsorted means no `sort`/`dir` param at all, at which point each query's own default ordering applies (date for Transactions). `useSortState()` (client, `src/components/table/use-sort-state.ts`) and `parseSortParam()` (server, `parse-sort-param.ts`) are the shared implementation — see Design system.
    - **Sorting and pagination happen at the database level** via the `transactions_expanded` view (see Database section) — `getActiveTransactions()` queries that view with real `.order()`/`.range()` and an exact count, instead of fetching everything and sorting/paginating in JS. The view flattens Entity/Wallet/Category names (and a computed `total`) onto each row specifically so sorting by those joined columns is just an ordinary `.order("entity_name", ...)` — PostgREST can't order a top-level query by an embedded resource's column directly, which is what made this worth a view rather than fighting that limitation. `page.tsx` re-fetches clamped to the last valid page if a filter change shrinks the result set out from under whatever page was requested.
    - Changing any filter or sort restarts the scroll list from the server's fresh first span (see the load-as-you-scroll bullet above for the `key` mechanism). `setFilterParams` merges into the querystring rather than replacing it, which is what makes the header filters, the toolbar search, the date range, and the quick-filter toggles stack instead of clobbering each other; it also strips a stale `page` param so a bookmark made before pagination was removed doesn't carry one.
    - **Default view = the current month** (2026-08, explicit user direction). A bare `/transactions` visit **redirects** (`page.tsx`) to `?from=<1st>&to=<last>` of the current month, so the URL stays the single source of truth (the date-range filter shows "This month" active, its fields populated) and `loadMoreTransactions` — which re-parses the querystring — stays consistent. The redirect is **skipped** whenever the URL already expresses a period intent: a `from`/`to` range, a Taxes invoice-date drill-down (`invoice_from`/`invoice_to`), or an explicit **All time** (`all=1`). **Balance view (`balance`) is *not* excluded** (2026-08 — corrected from a first pass that excluded it): it shares the exact same date default as the normal list, so the date range/preset never changes just by entering or leaving balance view — the `BalanceViewControl` merges `balance` in/out without touching `from`/`to`/`all`, and both views default to this month. A month default suits balance view specifically (it's used to reconcile a wallet against its monthly statement, and the running balance stays cumulative — carried in from all prior history — so a single month reads exactly like a statement: opening balance, that month's moves, closing balance). Because "All time" used to be the plain absence of a range (which now *means* this-month), the `DateRangeFilter`'s **All time** preset carries an explicit **`all=1`** marker to opt out of the default; every other preset clears it, and `all=1` counts as all-time only while no `from`/`to` is set. `parseTransactionListQuery` ignores `all` (it's just a redirect-suppressor — absent from/to already means "no date filter").

  - **Historical import** (2026-07, `transactions/import/`, `exceljs` dependency) — a permanent "Import" button next to Add transaction, for bulk-loading the user's pre-existing accounting spreadsheet (a fixed personal format: `Date, Account, Income, Expense, Category, Counterparty, Description, VAT, Bacon` columns; header names are matched, not fixed positions, so a reordered sheet still works). Every row becomes a plain Income or Expense transaction — the user represents wallet-to-wallet transfers as an expense-row/income-row pair in their spreadsheet rather than one row, and explicitly chose (2026-07) to keep importing them that way rather than have the importer try to detect and merge pairs into a real Transfer, since a reliable signal to detect a pair doesn't exist in the data. A 3-step flow rather than the app's usual single-form `ModalShell` pattern, since there's no single "submit": **upload** (pick the `.xlsx`) → **preview** (`parseImportFile()`, a pure read/compute pass — nothing is written yet) → **commit** (`commitImport()`, the actual writes, given exactly the rows the preview already resolved, so the file is parsed only once). Amounts in the file are **totals**, not net — `net = total / (1 + rate/100)`, same formula/rounding as the transaction form's own Total mode. Missing Categories/Entities/Wallets referenced by the file are auto-created (explicit user direction); a missing/unrecognized VAT rate is **not** auto-created, it fails that row instead (VAT rates are few and deliberate, unlike the other three). One hardcoded alias, `WALLET_ALIASES` (`import-actions.ts`) — the user's spreadsheet calls their bank wallet "Alpha", matched to the existing "Alpha Bank" wallet rather than becoming a second, separate wallet (confirmed explicitly, not guessed — silently creating a duplicate would have split that account's real balance history across two rows). A blank Description falls back to that row's Category name; the "Bacon" column feeds the Invoice-button state (see that bullet above) via the same `resolveInvoiceMonthInput()` — a 1–12 value sets `invoice_month` directly per-row (not "the current month" — confirmed explicitly, since the phrasing was ambiguous), 13 sets `invoice_not_required`, and anything else (blank, or a stray `0` left over from before the user standardized the sheet on 1–13) clears both. The preview shows aggregate counts/totals and the full list of new wallets/categories/entities rather than a per-row table (825 rows isn't something a human can usefully eyeball row-by-row; the aggregate + an error list is the meaningful review surface) — any row that fails to resolve (bad date, no income/expense amount, unrecognized VAT rate) is listed with its reason and simply excluded from the commit rather than blocking the whole import. `commitImport()` writes in chunks of 200 rather than one all-or-nothing database transaction (no RPC/stored procedure) — an accepted tradeoff for a single-user one-off tool: every write is a normal insert, so a partial failure is fully recoverable by hand (soft-delete the partial batch, fix the data, re-run) rather than corrupting anything, and a failure message reports exactly how many rows made it in before it. `next.config.ts` raises the Server Action body-size limit to 10mb (default is 1mb) as headroom for a larger file than the one this was built against.

- **Wallets** (`/wallets`) — Full CRUD list of where money is held (bank accounts, cash, etc.). The baseline `getWalletBalances()` adds every active transaction's effect on top of, instead of implicitly starting at zero — set once when a wallet is created (typically to whatever that account actually held before the app started tracking it) but stays an ordinary editable field on the edit modal in case it needs correcting, per explicit user direction ("added once and never changed but still needs to be editable"). Deliberately **not** shown as its own column on the Wallets list (explicit user direction — only the edit modal needs it, the list's existing Balance column already folds it in transparently) — `getActiveWallets()`/`getWalletsList()` still select it (needed to seed the edit modal's default value), just don't render it as a `<td>`. `getWalletTransactionsWithBalance()` (`transactions/queries.ts`, the balance-view running total) takes it as a `startingBalance` param and seeds its running walk from it too, so the two balance surfaces (Wallets list, Transactions balance view) can never disagree. - **Taxes** (`/taxes`, redesigned 2026-07) — Read-only throughout; not a CRUD list, there's nothing to store, everything here is a live aggregate over transactions. `/taxes` itself is a small list of tax types (`tax-types.ts` — a **code-defined array, not a user-editable table** like Categories/VAT rates, since tax rules are law-defined rather than arbitrary user data; currently just VAT, add a new entry plus its own `/taxes/[slug]/page.tsx` when a second tax type is needed, since each one's computation is genuinely different — no single generic page could serve all of them) shown as cards. Each card shows **two figures**: "Payable this month" and "This month's net", both for the current period, both read directly off `getMonthlyVatLedger()` (`payableThisMonth`/`net` — see below; an earlier version of this card showed a lifetime `SUM(vat_amount)` across every transaction, which turned out to be actively misleading since it added input and output VAT together instead of netting them, then a version after that naively used "last month's raw net" as the payable figure before the rollover/installment ledger below existed — both since replaced). As of 2026-08 there are **two** tax types (VAT, Withheld tax) and `taxes/page.tsx` computes each card's two figures **per `tax.slug`** (a `figures: Record<TaxTypeSlug, …>` map): VAT shows Payable this month / This month's net (off `getMonthlyVatLedger()`), Withheld shows Payable this month / Withheld this month (off `getMonthlyWithheldLedger()`). Each tax type stays genuinely distinct (VAT's payable folds in rollover/installments; withholding's is just last month's collected) — a future third type adds its own entry to that map rather than being forced into a shared shape.
  - **Withheld tax** (`/taxes/withheld`, 2026-08) — the withholding-tax remittance ledger, **much simpler than VAT** (no credit rollover, no installments): withholding collected in a month is remitted to the state by the end of the **next** month. `getMonthlyWithheldLedger()` (`taxes/queries.ts`) sums `withheld_amount` on **expense** transactions per month (the "we withhold and remit on the contractor's behalf" case the user described — income withholding, if ever entered, is the client's liability and isn't summed here) attributed to the transaction's **payment date (`date`)**, not `invoice_date` — the one place withholding and VAT deliberately key off different dates ("this month when we go to pay the contractor"). Walks every month (gap-filling, through the later of latest-activity or current) threading the previous month's withholding forward: each row exposes `withheld` (collected this month, = payable next month) and `payableThisMonth` (= last month's withholding, due to the state now). Built on the shared table template like `/taxes/vat` (columns Month | Withheld this month | Payable this month; no search/Add; oldest-first; `getMonthlyWithheldList()` filters/sorts the already-computed ledger, same split as VAT). Each Month links into `/transactions?from=…&to=…&type=expense` (by payment date). `payableNextMonth` isn't a column — it always equals `withheld`, so showing both would read as duplication.
  - **VAT rollover and installments** (2026-07, `taxes/queries.ts`, researched and confirmed against Greek VAT rules — see chat, and confirmed explicitly by the user): a period's raw net (`net` = output − input) isn't what's actually owed — `getMonthlyVatLedger()` walks every period **chronologically** (oldest first) threading two pieces of running state forward: a **credit carry** (a negative net, "πιστωτικό", rolls forward indefinitely to offset a later period's debit — this app doesn't model the real 5-year statute of limitations on unused credit, since a single ongoing company will use it long before that's relevant) and a **deferred installment** (a positive net after credit, "χρεωστικό", over €100 is split into two equal interest-free installments — half due with that period's own filing, half due the following month; €100 or under is paid in full immediately). The installment *option* is always treated as taken — there's no toggle, matching explicit user direction. Each period's row exposes `rolloverIn` (credit brought in), `payableThisMonth` (this period's own now-due share **plus** whatever the previous period deferred in), and `payableNextMonth` (the half **this** period's own filing pushes into the next one). Every month between the earliest VAT-bearing transaction and the later of (latest transaction) or (today) is walked, including zero-activity gap months — a deferred installment or carried credit still has to pass *through* a quiet month to reach the next one with real activity, so skipping gaps would silently break the chain. This ledger walk always runs over the **complete, unfiltered** history (`getMonthlyVatLedger()`) — later periods depend on every one before them, so it can never be computed over a filtered subset; `getMonthlyVatList()` filters/sorts/paginates the *already-computed* result for display, the same split (and the same reasoning) `getWalletTransactionsWithBalance()` already uses.
  - **`/taxes/vat`** — built on the shared table template (2026-07, explicit user direction — an earlier version hand-rolled a plain table with no per-column filters, breaking the app's standing "every table is the same" rule). All seven columns (Month, Income VAT, Expenses VAT, Net VAT, Roll over, Payable this month, Payable next month) are sortable and filterable — Month via `HeaderDateRangeFilterPopover` (comparing against the 1st of each period), the six money columns via `HeaderNumberRangeFilterPopover` — same shared filter popovers as every other table. No pagination (2026-07 — no table in the app paginates now); every matching month renders and scrolls. Deliberately **no search box and no Add button** (nothing free-text to search, nothing to create — every row is a computed month, not a record) and **no `max-w` cap** (seven columns need the room, same reasoning as Transactions). Defaults to **oldest-first** (an earlier version defaulted newest-first, reasoned as more useful for a tax report — the user overrode that to match the rest of the app's oldest-on-top convention). Sorting by anything other than Month will make Roll over/Payable this-next month stop reading as a coherent chain (each row depends on the one before it) — same accepted, documented tradeoff the old wallet ledger's running-balance column already had.
  - **VAT** (`/taxes/vat`) — a month-by-month breakdown table (newest month first): Output VAT (from income) | Input VAT (from expense) | Net, per Greek VAT law as explicitly described by the user: VAT collected on income is owed to the state each period, reduced by VAT already paid on expenses in that same period — a net *negative* month is a credit, not a payable amount (no automatic carry-forward to the next period is computed; shown as a plain signed number for the user to interpret). `getMonthlyVat()` (`taxes/queries.ts`) fetches every income/expense row and groups by `invoice_date`'s year+month in JS (`row.invoice_date.slice(0, 7)`) — not `date`, per the Invoice date rule above. Aggregated in JS rather than a SQL `GROUP BY`, the same pattern `getWalletBalances()` already uses: PostgREST doesn't support arbitrary grouping through the standard client, and this app's data volume makes an in-JS reduce entirely reasonable. Deliberately **doesn't use the shared table template** — it's a fixed, small set of calendar months, not a searchable/sortable/paginated list, so none of that machinery applies. Each month is a link into `/transactions?invoice_from=<first-of-month>&invoice_to=<last-of-month>` — "which transactions make up this month's VAT" reuses Transactions' existing table/filters entirely rather than a bespoke breakdown UI on the Taxes page itself.

## Technical sections

- **Framework**: Next.js 16 (App Router, Turbopack), TypeScript, Tailwind CSS v4, ESLint. Scaffolded with `create-next-app`.
- **Data/validation libs**: `zod` validates every Server Action's input (see `schema.ts`/`vat-rate-schema.ts` next to each feature's `actions.ts`) — `parseOrThrow()` (`src/lib/validation.ts`) parses `formDataToRecord(formData)` (`src/lib/form-data.ts`) against the schema and throws a clean, user-facing message on the first issue, rather than trusting raw `FormData` casts. The transaction schema is a `discriminatedUnion` on `type`, mirroring the `transactions_type_fields_check` DB constraint at the app layer (income/expense need wallet+VAT rate, transfer needs two distinct wallets and nothing else) — validating both places is intentional: the app layer gives an immediate, friendly error; the DB constraint is the actual source of truth and can't be bypassed by an app-layer bug. `@tanstack/react-query` was **removed** (2026-07) — it had been mounted app-wide via a root `Providers` component but never used for a single query, so it was shipping ~27KB of JavaScript to every page for nothing. There is no client-side data-fetching library now: every read is a Server Component query, every write a Server Action. Don't reintroduce one without a concrete need.
- **Generated Supabase types**: `src/lib/supabase/database.types.ts` (generated via the Supabase MCP's `generate_typescript_types` — regenerate after schema-changing migrations, never hand-edit) is wired into both `createClient()` factories (`lib/supabase/client.ts`/`server.ts`) via `createBrowserClient<Database>()`/`createServerClient<Database>()`, so `.from()`/`.select()` calls are checked against the real schema (a typo'd table/column name is a compile error).
  - **This only works if the client's type is carried through to the call site — use `TypedSupabaseClient` (`src/lib/supabase/types.ts`), never the bare `SupabaseClient` from `@supabase/supabase-js`.** The bare one defaults its schema parameter to `any`, which silently erases every bit of the checking above. This was the actual state of the app until 2026-07: both factories were correctly typed, but *every* query helper and Server Action declared `supabase: SupabaseClient`, so the generated types were providing **zero** real safety anywhere — this section previously claimed otherwise, and was wrong. Fixed by adding the alias and using it across the data layer (verified by confirming a deliberate `.from("wallet_balnces")` typo now fails the build; before, it compiled clean). The first thing it caught was a real latent mismatch in `attachVatLines()` — see the numeric gotcha below.
  - Existing hand-written domain types (`Transaction`, `Entity`, etc. in each feature's `queries.ts`) are unaffected — they're still what the rest of the app uses, since each query function's `.returns<T>()` call overrides the generic-inferred type anyway. **Gotcha**: the generator types every Postgres `numeric` column as TS `number`, but the Supabase JS client actually returns `numeric` values as strings at runtime — don't trust that file's `number` label for `net`/`vat_amount`/`rate`/`total`; keep doing `Number(...)` explicitly, same as before. Every query states its own row shape via `.returns<T>()` for exactly this reason — `attachVatLines()` (`transactions/queries.ts`) was the one that didn't, so it silently inherited the generated `net: number` and pushed it into a `string` field; harmless at runtime (numerics really are strings) but an invisible lie until the typed client above exposed it. If a new query needs a `numeric` column, declare its row type explicitly rather than leaning on the generated one.
- **Auth/session plumbing**: `@supabase/ssr` with three client setups:
  - `src/lib/supabase/client.ts` — browser client
  - `src/lib/supabase/server.ts` — server client (Server Components/Actions)
  - `src/lib/supabase/proxy.ts` + `src/proxy.ts` — session-refresh and route protection. Next.js 16 renamed "middleware" to "proxy" (file `proxy.ts`, function `proxy`) — this app follows that convention. Auth check uses `supabase.auth.getClaims()` (not `getSession()`/`getUser()`), per current Supabase guidance.
  - Unauthenticated visitors are redirected to `/login` for any route except `/login`, `/signup`, and `/auth/*`.
- **Page structure**: `src/app/(app)/` is a route group holding the authenticated app shell — `layout.tsx` (top bar + side nav, see Main sections), `top-bar.tsx`/`side-nav.tsx`/`user-menu.tsx`/`notification-bell.tsx` (shell pieces), `page.tsx` (Home, `/`), `transactions/page.tsx` + `transactions/actions.ts` (`/transactions`), `account/page.tsx` (`/account`), `options/page.tsx` (`/options`). ## Formatting conventions

Greek-style formatting is used everywhere the app displays dates/numbers: dates as `dd/mm/yyyy`, numbers with `.` as the thousands separator and `,` as the decimal separator, always rounded to exactly 2 decimals. Shared helpers live in `src/lib/format.ts` (`formatDate`, `formatAmount`, `computeTotal`, `formatMonthYear` — 2026-07, renders a "yyyy-mm" tax-period key as e.g. "July 2026" for the Taxes → VAT monthly breakdown; deliberately English month names via a fixed array rather than `toLocaleDateString`, since the rest of the app's UI text is English even though its date/number formatting is Greek-style) — use these instead of ad-hoc formatting/arithmetic whenever displaying a date or amount anywhere in the app.

**Date inputs (`DateField`)** — 2026-08, explicit user direction, two rounds. Date *entry* no longer uses the native `<input type="date">`, whose on-screen format follows the browser/OS locale (it showed American `mm/dd/yyyy`) and can't be changed from code. `src/components/date-field.tsx` is a locale-independent replacement whose order is always `dd/mm/yyyy`, while it reads/emits an ISO `yyyy-mm-dd` value — so every consumer (Server Actions, `date` columns, `from`/`to` URL filter params) is unchanged; only the on-screen format is ours. **It is a segmented field, not a text box** (the first cut was a plain text input and had bad UX): three numeric segments (day/month/year) with `/` separators, each selected on focus/click, auto-advancing to the next as it fills (a first digit that can't start a two-digit value — day 4-9, month 2-9 — advances immediately; a full pair advances and is clamped to its range, day→31/month→12), so digits never spill across segments (the old text box let `14`+`7` become `147/8/26`) and you never type the `/` yourself. Arrow up/down nudges a segment; a 1-2 digit year is read as 20xx on blur; an incomplete/invalid date on blur snaps back to the last valid value. The dd/mm/yyyy→ISO parse is `displayToIso` in `lib/format.ts` — strict, rejecting impossible dates like 31/02 by round-tripping through a `Date` so a bad value becomes "" rather than a plausible lie; `z.iso.date()` in `schema.ts` is the server-side backstop. The box chrome lives on the wrapper (`formFieldBoxClass` in `form-styles.ts`, a `focus-within` sibling of `formInputClass`) since the segments are the focus targets, not the box. It keeps a real calendar popup via the native picker's `showPicker()` behind a calendar button — shown everywhere a date is entered **except** the transaction-entry modals (`transaction-form-dialog.tsx` Add/Edit and `reconcile-modal.tsx`, both `showCalendar={false}`), where the user wants keyboard-only fast entry; the two filter entry points keep the calendar. **Amount inputs** (2026-08, explicit user direction) are plain `text` inputs with `inputMode="decimal"`, **not** `<input type="number">` — Chrome ties a number input's accepted decimal separator to the OS/browser locale, so on a Greek locale (decimal ",") the user couldn't type the decimal at all. They accept either "," or ".": `sanitizeAmountInput`/`parseAmountInput` in `lib/format.ts` filter keystrokes to digits + separators and turn the string into a number (a "," is the decimal point and any "." are thousands separators; without a "," the "." is decimal). Every amount reaches the server already normalized to a number — income/expense via the hidden `lines` JSON, transfer and reconcile via a hidden `net` field — so a "," is never submitted raw. This covers the add/edit dialog (`transaction-form-dialog.tsx`) and the reconcile modal.

## Design system

The app has a real visual identity now (2026-07), not default-Tailwind styling — this replaced a "crude"-looking first pass across every page.

- **Theme**: Light / Dark / Follow system, chosen in Options → Appearance (`theme-switcher.tsx`). Preference is a cookie (`yolt-theme`, `src/lib/theme.ts`), not per-account DB state — deliberate, since this is a device-level preference, not something that needs cross-device sync. `getThemePreference()` reads it server-side in the root layout (`src/app/layout.tsx`) to set `data-theme` on `<html>` **before first paint**, which is what avoids a flash of the wrong theme. When the preference is "system", `data-theme` is omitted entirely and a `@media (prefers-color-scheme: dark)` rule (scoped to `:root:not([data-theme])`) decides, purely via CSS — no JS involved for that case.

Accepted, deliberate tradeoff for correct SSR theming — not a regression to "fix."

- A thrown error inside a `startTransition(async () => { await action(...) })` callback does **not** reach an Error Boundary and is *not* automatically shown anywhere — it becomes a silent unhandled promise rejection unless caught explicitly. Every modal form dialog and delete button wraps its action call in try/catch (dialogs: `useState<string|null>` displayed near the buttons; delete buttons: `alert()`) — keep this pattern for any new Server-Action-calling client component, don't assume a thrown error will surface on its own.
- **Server Actions must RETURN `{ error }`, not throw, for any message meant for the user (2026-08-24, standing convention).** Next.js **sanitizes thrown Server Action errors in production** — the client only ever gets a generic "an error occurred… digest", never the real message (a security default; it's why an invite failure once showed that opaque page). A *returned* value passes through intact. The shared helper is **`formAction(fn)`** (`src/lib/action-result.ts`, returns `ActionResult = { error?: string }`): it runs the action body, catches a thrown error and returns its `.message`, and `unstable_rethrow`s framework control-flow (`redirect()`/`notFound()`). **Every CRUD/modal Server Action is wrapped in it** — one line: `export async function addThing(fd) { return formAction(async () => { …body that may throw… }); }`; `parseOrThrow` validation messages surface this way too. The client side displays a returned `error`: `useFormAction`/`ModalShell` and `DeleteButton` handle it built-in (a returned `{}`/void behaves as success, so it's additive), and the few hand-rolled callers (`transaction-form-dialog`'s Add-flow `runAction`, `lead-edit-form`, `lead-add-modal`) read `result?.error`. **Exceptions that deliberately stay as-is:** the inline quick-edits `updateLeadNextStep`/`updateLeadStatus` (their editors already handle a throw and don't render a message), `loadMoreTransactions` (returns rows, not a form action), and the `redirect(?message=)`-based auth/account forms (login, set-password, email/password — they surface errors via a redirect param, not a thrown/returned value). **Write any new user-facing action with `formAction` + return, never a bare throw.**

- **When this app feels slow, suspect geography and round-trip *count* before suspecting the queries** (2026-07 performance pass). Measured, not guessed: the main Transactions list query executes in **~2.4ms** server-side (`explain analyze`, 831 transactions) — its *planning* time (~12ms) is larger than its execution. The database has never been the bottleneck at this scale. What actually cost seconds was (a) Vercel running in `iad1` while Supabase runs in `eu-west-1`, making every round trip transatlantic (see the Hosting/deploy bullet — now pinned to `dub1`), and (b) how many round trips each action made *in sequence*. A Server Action's perceived cost is roughly `(number of sequential round trips) x (region distance)`, and after `revalidatePath` the current page re-renders and re-runs its queries **before the response returns** — so the page's own query count is on the save's critical path too, not just the action's. Prefer `Promise.all` over sequential `await`s, fetch small lookup tables once instead of per-row, and don't add a round trip to a hot path without noticing. Remaining known-but-accepted sequential hops: `transactions/page.tsx` awaits wallets before the rest (balance view needs it to pick a query path), and `attachVatLines()` is a second query after the main list (a one-to-many can't flatten onto the view). Both are ~3ms same-region now; they were only worth restructuring back when they cost 75ms each.
- **Postgres RLS gotcha (learned the hard way, don't repeat it on future tables)**: an `UPDATE`'s resulting row must satisfy the table's `SELECT` policy too, not just the `UPDATE` policy's own `WITH CHECK` — this is enforced unconditionally, regardless of what the `UPDATE` policy's check says. So a SELECT policy that filters out `is_deleted = true` makes it *structurally impossible* for a user to ever set `is_deleted = true` on their own row (the resulting row would be invisible to their own write, which Postgres blocks outright — this produces the exact error `new row violates row-level security policy`). The fix: for any table with a soft-delete column, the SELECT RLS policy must stay unrestricted on that column (just `auth.uid() = user_id`, no `is_deleted` condition) — do the "hide deleted rows" filtering only in a shared app-level query helper. `categories` (2026-07) already followed this correctly; keep doing so for any future table that gets soft-delete.
